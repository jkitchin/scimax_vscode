* Introduction

Scimax VS Code includes a command-line interface (CLI) that provides access to many features without needing to open VS Code. This is useful for:

- Batch operations (exporting multiple files)
- Integration with other tools and scripts
- Quick lookups from the terminal
- CI/CD pipelines for documentation

The CLI reads from the same SQLite database that the VS Code extension builds, so you get consistent results between the editor and command line.

* Installation

** From the Extension

If you have the extension installed, the CLI is included. After building the extension:

#+begin_src bash
# From the extension directory
npm run compile

# Run directly
node out/cli/index.js --help

# Or use npx (if in the extension directory)
npx scimax --help
#+end_src

** Global Installation

To use ~scimax~ from anywhere:

#+begin_src bash
# From the extension directory
npm link

# Now available globally
scimax --help
#+end_src

To unlink later:
#+begin_src bash
npm unlink scimax-vscode
#+end_src

* ✅ Configuration
CLOSED: [2026-04-12 Sun 19:48]

The CLI automatically uses the same database as the VS Code extension. It looks in VS Code's global storage location:

| Platform | Database Path                                                                                   |
|----------+-------------------------------------------------------------------------------------------------|
| macOS    | =~/Library/Application Support/Code/User/globalStorage/jkitchin.scimax-vscode/scimax-db.sqlite= |
| Linux    | =~/.config/Code/User/globalStorage/jkitchin.scimax-vscode/scimax-db.sqlite=                     |
| Windows  | =%APPDATA%/Code/User/globalStorage/jkitchin.scimax-vscode/scimax-db.sqlite=                     |

The database is created and maintained by VS Code when you open a folder with org files. The CLI reads from and writes to this same database.

** Override Database Path

You can override the database path with the =--db= flag:

#+begin_src bash
scimax db stats --db /path/to/custom.db
scimax search "query" --db /path/to/custom.db
#+end_src

** Custom Configuration (Advanced)

For advanced setups, you can create =.scimax/config.json= in your project directory to specify a custom database path:

#+begin_src json
{
  "dbPath": "/custom/path/to/scimax.db"
}
#+end_src

The CLI checks for this file only if the VS Code global storage database is not found.

** Export

Export org files to HTML, LaTeX, or PDF.

#+begin_src bash
# Export to HTML
scimax export paper.org --format html

# Export to LaTeX
scimax export paper.org --format latex

# Export to PDF (requires pdflatex/latexmk)
scimax export paper.org --format pdf

# Export to PDF, printing the LaTeX log tail if compilation fails
scimax export paper.org --format pdf --show-log

# Export to Beamer slides (.tex)
scimax export slides.org --format beamer

# Compile Beamer slides to PDF
scimax export slides.org --format beamer-pdf

# Specify output file
scimax export paper.org --format html --output build/paper.html

# With bibliography
scimax export paper.org --format html --bib references.bib

# With specific CSL style
scimax export paper.org --format html --bib refs.bib --csl ieee
#+end_src

The export command automatically looks for bibliography files in the same directory (=refs.bib=, =references.bib=, or =<filename>.bib=).

When a PDF compile fails, the CLI prints the first LaTeX error and its =.tex=
line, points to the full =.log=, and deletes the incomplete PDF so a broken build
is not mistaken for a good one. Use =--show-log= (or =--verbose= / =-v=) to also
print the tail of the log. See [[file:10-export.org][Export]] for details.

** ✅ Tangle
CLOSED: [2026-07-11 Sat 09:08]

Extract source blocks to their =:tangle= target files (org-babel tangling). Each block with a =:tangle <filename>= header argument is written to that file, with multiple blocks targeting the same file concatenated in document order. Blocks with =:tangle no= (or no =:tangle= header) are skipped. Noweb references (=<<name>>=) are expanded by default for blocks marked =:noweb yes= or =:noweb tangle=.

#+begin_src bash
# Tangle all blocks in a file to their :tangle targets
scimax tangle setup.org

# Only tangle specific named blocks (matches #+NAME: of the block)
scimax tangle setup.org --only init,config

# Disable noweb reference expansion
scimax tangle setup.org --no-noweb

# Structured JSON output (files written, block/line counts, errors)
scimax tangle setup.org --json
#+end_src

Relative =:tangle= paths are resolved against the directory of the source file, and parent directories are created as needed. Note that =--only= filters *named* blocks; unnamed blocks with a =:tangle= target are always tangled.

** Journal

Open or create journal entries from the terminal.

#+begin_src bash
# Open today's journal (creates if needed)
scimax journal

# Open a specific date
scimax journal tomorrow
scimax journal yesterday
scimax journal friday
scimax journal --date "next monday"
scimax journal --date 2026-03-15
scimax journal --date +2d
scimax journal --date -1w

# JSON output (for scripting)
scimax journal --json
#+end_src

The journal directory is configured via =scimax.journal.directory= in VS Code settings. New entries use the default template (customizable via =scimax.journal.customTemplate= setting).

Supported date expressions: today, tomorrow, yesterday, day names (monday, fri), next/this day (next friday, this monday), relative (+2d, -1w, +3m), month+day (jan 15), ISO dates (2026-03-15).

** Project

Fuzzy-select and open a known project in VS Code.

#+begin_src bash
# Interactive fuzzy selection (uses fzf if available)
scimax project

# Pre-filter with a query
scimax project scimax

# List all known projects
scimax project --list

Projects are pulled fresh from the scimax database each time. The extension registers projects automatically when you open folders in VS Code.

When =fzf= is installed, the interactive selection uses fuzzy matching. Otherwise, a numbered list is displayed.

** ⚠️ Tasks

Project management over org task graphs. Answers "what should I work on
next", who is overloaded, what is blocked, and what the long pole is.

Note that =scimax task= and =scimax project= are unrelated despite the
similar-sounding names: =scimax project= opens VS Code workspaces, while
=scimax task= reads task metadata inside org files.

#+begin_src bash
# What to work on now, ranked and explained
scimax task next

# Open tasks, filtered
scimax task list --ready
scimax task list --blocked
scimax task list --assignee priya

# Workload by assignee
scimax task who

# One task: what blocks it, what it unblocks
scimax task show synth

# Critical path through the remaining work
scimax task path

# Mark done (refuses if blocked) and set an assignee
scimax task done synth
scimax task assign xrd priya

# Which files contain tasks
scimax task files
#+end_src

*** Task Model

A task is a heading carrying an =:ID:= property. The relevant properties are:

| Property    | Meaning                              | Example              |
|-------------+--------------------------------------+----------------------|
| =:ID:=      | Task identifier (required)           | =synth=              |
| =:ASSIGNEE:=| Who owns it                          | =liam=               |
| =:EFFORT:=  | Estimated work, =Nd= or =Nh=         | =5d=                 |
| =:DEPENDS:= | Explicit blockers, space-separated   | =id:design id:xrd=   |
| =:ORDERED:= | On a parent: children run in order   | =t=                  |

Both blocking sources are honored, so =--ready= and =--blocked= match what the
editor enforces. =scimax task done= refuses a blocked task unless =--force= is
passed, and reports which tasks the completion unblocked.

*** File Selection

File selection is global by default. The database spans every indexed file, so
=scimax task next= gives the same answer from any directory: it picks the file
with the most task metadata anywhere.

| Flag            | Effect                                            |
|-----------------+---------------------------------------------------|
| (none)          | The file with the most tasks, anywhere            |
| =--local=       | Only files under the current directory            |
| =--file <path>= | That file                                         |

Run =scimax task files= to see the candidates with their task counts.

*** Options

| Option          | Description                              |
|-----------------+------------------------------------------|
| =--file <path>= | Project file to operate on               |
| =--local=       | Confine discovery to the current directory |
| =--json=        | Structured output                        |
| =--force=       | Allow =done= on a blocked task           |

*** Limitations

- =done= does not write a =CLOSED:= timestamp, and does not regenerate
  =project-table= or =gantt= dynamic blocks; refresh those in the editor.
- =:ORDERED:= sequences direct children only, not deeper descendants.
- Task ids resolve within one file, so cross-file =:DEPENDS:= is not followed.
- Effort totals count only =Nd= and =Nh=; anything else is reported as
  unestimated.

*** ✅ Sync
CLOSED: [2026-07-11 Sat 09:08]

Bring the database into agreement with the configured scan roots and the filesystem in one pass: pick up new files, refresh changed files (mtime-based), refresh in-scope files that are stale, and prune entries for files that no longer exist.

Scan roots are unioned from:
1. =scimax.db.include= (VS Code settings)
2. =scimax.journal.directory=
3. =scimax.agenda.include=
4. NotebookManager projects (every project you have opened in VS Code, persisted in =notebooks.json=)

Files in the database that do not fall under any current root are still refreshed if they exist and their mtime has advanced; otherwise they are left alone.

#+begin_src bash
# Default daily driver
scimax db sync

# Preview what sync would do without changing the DB
scimax db sync --dry-run

# Show a line per file (in addition to the summary)
scimax db sync --verbose
#+end_src

Output:
#+begin_example
Database: ~/Library/Application Support/Code/User/globalStorage/jkitchin.scimax-vscode/scimax-db.sqlite

Scan roots (3):
  ~/Dropbox/org
  ~/Dropbox/journal
  ~/Dropbox/projects/scimax_vscode

sync complete in 1.4s
  +12 new
  ~5 updated
  -2 removed
  1834 unchanged
#+end_example

The summary uses these markers:

| Marker | Meaning                                                 |
|--------+---------------------------------------------------------|
| =+=    | New file added to the database                          |
| =~=    | Existing file re-indexed (mtime newer)                  |
| =*=    | Out-of-scope file refreshed because mtime advanced      |
| =-=    | File removed from the database (no longer on disk)      |
| =     | Unchanged                                                |

*** ⚠️ Prune Excluded Files

Remove database entries that the current exclude rules would reject.

=scimax db sync= deliberately keeps an entry whose file still exists on disk,
even when that file is outside the configured scan roots — otherwise files added
by other means would vanish on every sync. The consequence is that tightening
=scimax.db.exclude=, or upgrading to a version that adds a new built-in
exclusion, leaves the old rows in place. =prune= is what clears them.

#+begin_src bash
# See what would go, grouped by the pattern that caught it
scimax db prune --dry-run

# Remove them
scimax db prune

# Machine-readable
scimax db prune --json
#+end_src

Output:
#+begin_example
Database: ~/Library/Application Support/Code/User/globalStorage/jkitchin.scimax-vscode/scimax-db.sqlite
Exclude patterns: 22
Indexed files: 58713
Matching exclude rules: 26570
Mode: dry-run (no changes will be written)

    23872  **/node_modules/**
     2574  **/Code/User/History/**
      120  **/build/**
        4  **/Code/User/globalStorage/**

Would remove 26570 file(s). Re-run without --dry-run to apply.
#+end_example

Always run =--dry-run= first and read the per-pattern breakdown. A pattern that
catches far more than you expected is usually a pattern that is too broad.

**** ⚠️ Scheduling Automatic Syncs

Prefer =db sync= over =db scan= for scheduled runs: it covers every configured
scan root at once, refreshes changed files, and prunes entries whose files are
gone. =db scan= only adds one directory.

***** macOS (launchd)

On a laptop, use =launchd= rather than =cron=. If the machine is asleep at the
scheduled time, launchd runs the job at the next wake; cron simply misses it.

A wrapper script keeps the log timestamped, bounded, and free of overlapping
runs. Save it as =~/.local/bin/scimax-db-sync.sh= and =chmod +x= it:

#+begin_src bash
#!/bin/bash
set -uo pipefail

# launchd starts jobs with a bare environment, so spell out the PATH.
export PATH="/opt/homebrew/bin:/usr/bin:/bin:/usr/sbin:/sbin"

LOG_DIR="$HOME/Library/Logs/scimax"
LOG="$LOG_DIR/db-sync.log"
LOCK="$LOG_DIR/db-sync.lock"
MAX_LOG_BYTES=$((5 * 1024 * 1024))

mkdir -p "$LOG_DIR"

if [ -f "$LOG" ] && [ "$(stat -f%z "$LOG")" -gt "$MAX_LOG_BYTES" ]; then
    mv -f "$LOG" "$LOG.1"
fi

# mkdir is atomic: a run that overlaps the previous one backs off rather than
# competing for the database write lock.
if ! mkdir "$LOCK" 2>/dev/null; then
    echo "[$(date '+%Y-%m-%d %H:%M:%S')] skipped: a sync is already running" >> "$LOG"
    exit 0
fi
trap 'rmdir "$LOCK" 2>/dev/null' EXIT

{
    echo "=== $(date '+%Y-%m-%d %H:%M:%S %Z') — scimax db sync ==="
    START=$(date +%s)
    scimax db sync
    STATUS=$?
    echo "--- exit $STATUS after $(( $(date +%s) - START ))s"
    echo
} >> "$LOG" 2>&1
#+end_src

Then =~/Library/LaunchAgents/com.USER.scimax-db-sync.plist=, here scheduled for
06:00 and 17:00:

#+begin_src xml
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>Label</key>
  <string>com.USER.scimax-db-sync</string>

  <key>ProgramArguments</key>
  <array>
    <string>/bin/bash</string>
    <string>/Users/USER/.local/bin/scimax-db-sync.sh</string>
  </array>

  <key>StartCalendarInterval</key>
  <array>
    <dict><key>Hour</key><integer>6</integer><key>Minute</key><integer>0</integer></dict>
    <dict><key>Hour</key><integer>17</integer><key>Minute</key><integer>0</integer></dict>
  </array>

  <key>StandardOutPath</key>
  <string>/Users/USER/Library/Logs/scimax/launchd.out</string>
  <key>StandardErrorPath</key>
  <string>/Users/USER/Library/Logs/scimax/launchd.err</string>

  <key>RunAtLoad</key>
  <false/>

  <key>ProcessType</key>
  <string>Background</string>
</dict>
</plist>
#+end_src

Load it, then prove it works instead of waiting until tomorrow:

#+begin_src bash
plutil -lint ~/Library/LaunchAgents/com.USER.scimax-db-sync.plist
launchctl bootstrap gui/$UID ~/Library/LaunchAgents/com.USER.scimax-db-sync.plist

launchctl kickstart -p gui/$UID/com.USER.scimax-db-sync   # run it now
launchctl print gui/$UID/com.USER.scimax-db-sync | grep -E 'state|runs|last exit'
tail -f ~/Library/Logs/scimax/db-sync.log
#+end_src

To change the schedule, edit the plist, then =launchctl bootout= and
=bootstrap= again — launchd caches the loaded copy.

#+begin_src bash
launchctl bootout gui/$UID/com.USER.scimax-db-sync
launchctl bootstrap gui/$UID ~/Library/LaunchAgents/com.USER.scimax-db-sync.plist
#+end_src

***** Linux (cron)

#+begin_src bash
crontab -e

# 6am and 5pm daily
0 6,17 * * * /usr/local/bin/scimax db sync >> ~/.local/state/scimax/db-sync.log 2>&1
#+end_src

Use an absolute path to the binary: cron's =PATH= is minimal and will not find a

**** Command Comparison

| Command                | Use Case                                                  |
|------------------------+-----------------------------------------------------------|
| =scimax db sync=       | Daily driver: discover, refresh, and prune in one pass    |
| =scimax db clear=      | Wipe the database (followed by =sync= for a full rebuild) |
| =scimax db scan <dir>= | Ad-hoc scan of a single directory                         |
| =scimax db check=      | Read-only integrity report (no changes)                   |
| =scimax db prune=      | Drop entries the exclude rules now reject                 |

- Use *sync* for routine maintenance, including the morning's first pass.
- Use *scan* for one-off directories outside the configured scan roots.
- Use *clear* + *sync* only when you genuinely need to start over.
- Use *prune* after changing =scimax.db.exclude=, or after an upgrade that adds
  a built-in exclusion.

The =rebuild= and =reindex= subcommands have been removed. Use =sync= (or =clear= + =sync=) instead.

* Limitations

The CLI has some limitations compared to the VS Code extension:

1. *Semantic Search*: Requires embeddings which need the embedding service configured in VS Code.

2. *Live Updates*: The CLI reads a snapshot of the database. Changes made to org files won't be reflected until you run =scimax db sync= or VS Code re-indexes them.

3. *Interactive Features*: No support for interactive features like completion or live preview.

4. *FTS Index*: =scimax db sync= populates the main tables but doesn't rebuild the FTS5 full-text index triggers. For full FTS support, use VS Code to create the initial database.
